# WI工作项维护规范

本文规定工作项从创建、准入、委托执行到状态维护、验收和结束的统一规则；[WI工作项文档模板](./WI工作项文档模板.md)提供统一文档结构、填写提示和示例，不另行定义规则。

## 1. 定义、定位、编号与适用范围

需要跨时段跟进的执行事项统一称为工作项（Work Item，简称 WI），编号采用 `WI-NN` 格式，其中 `NN` 为固定两位数字（如 `01`、`02`）。每个 WI 必须使用一个独立的 Markdown 文件维护，不得在同一文件中合并维护多个 WI。文件名采用 `WI-NN-任务名称.md`，文档标题采用 `WI-NN：任务名称`，同一 WI 的文件名与文档标题中的编号须保持一致。

编号仅在同一目录内唯一，不同目录（包括归档与非归档目录）可以重复；文档移出后，原目录可复用该编号。跨目录或长期引用使用带任务名称的文档路径链接，不只写编号。迁移或归档时保留原编号，目标目录存在编号冲突时重新编号，并同步更新文件名、标题和受影响的引用；重编号不改变工作内容、状态、委托或验收事实。

WI 是最小的独立承诺、委托和验收单元。它定义要交付的结果及执行约束，不是预先展开的操作脚本，也不要求对应 AI 的一次对话、一次提交或一个连续执行过程。

本规范适用于单个 WI 的定义、编号、字段与填写、创建粒度、建立、委托执行、状态记录和验收，覆盖产品功能、项目管理与人机协作、工程公共维护等领域，各领域使用相同的状态流。

WI 不以工作性质限制准入，适用于实现、维护、调研、决策等工作。正式建立 WI 须明确结果、边界和验收方式，能够独立委托和验收，并经负责人确认准入；创建要求见第 4 章。

项目管理机制、协作流程及规范模板的改进可作为 WI，按本规范定义和执行；候选区管理、项目目录规划、并行工作数量、例会及归档等具体管理机制不由本文规定。

工作所属的功能或主题通过其存放位置及关联资料表达；实际存放位置遵循项目已生效的目录约定。

## 2. 状态定义与转换

### 2.1 状态含义

`status` 记录正式 WI 的执行阶段或结束结果，是工作状态的唯一权威字段。目录位置表达管理归属及候选、正式工作、归档等文档生命周期阶段，不替代工作项状态。

| 状态 | 含义 |
| --- | --- |
| `ready` | 已审核准入、已承诺且可交接，尚未开始 |
| `in_progress` | 已接受委托并实际开始，尚未结束且未阻塞 |
| `blocked` | 启动或继续推进所需条件缺失，当前授权范围内已无可推进动作，必须等待外部条件或负责人处理 |
| `done` | 已产生可验证结果，完成标准满足、有证据且负责人已明确验收通过 |
| `cancelled` | 负责人已明确决定不再处理，并有取消原因 |

不增加 `draft`、`review`、`testing` 或 `archived` 状态；候选由候选区管理，验证和待验收事项由当前下一步表达，归档由目录表达。不使用“差不多完成”“待观察”“以后再说”等模糊状态。

### 2.2 允许的状态转换与判定条件

| 状态变化 | 成立条件 |
| --- | --- |
| 建立 WI，初始为 `ready` | 必要内容齐全，负责人确认目标、交付物、完成标准、边界和启动依赖，审核通过并正式建立；准入清单见第 4.2 节 |
| `ready → in_progress` | 已有明确委托，并开始首个实质执行动作；为交付物开展必要调查算开始，仅浏览 WI 或接受未来安排不算 |
| `ready / in_progress → blocked` | 当前执行者核实启动或推进条件缺失，且当前授权范围内已无可推进动作；负责人也可明确通知条件失效 |
| `blocked → ready` | 尚未开始的 WI 重新满足启动条件 |
| `blocked → in_progress` | 已开始的 WI 恢复可继续推进的条件，且具有有效委托（原委托仍有效或已取得有效的新委托） |
| `in_progress → done` | 完成标准满足、有可验证证据，且负责人已针对该 WI 明确验收通过 |
| `ready / in_progress / blocked → cancelled` | 收到负责人针对该 WI 的明确取消决定 |

解除阻塞时，由当前执行者核实客观条件及委托；涉及范围、权限或业务决定时由负责人确认。解除本身不构成执行委托或新增授权。

已开始的 WI 因委托到期、撤销或执行者变更而没有有效执行委托，且已无可推进动作时，进入或保持 `blocked`，记录待重新委托；不得退回表示尚未开始的 `ready`。其他条件已恢复但仍缺委托时，更新阻塞原因及下一步；取得有效新委托且推进条件满足后，恢复 `in_progress`。单纯尚未领取的 `ready` 不因此标记为阻塞。

### 2.3 易混淆情形

- 局部步骤受阻但仍有可推进动作时，保持 `in_progress`。
- 执行、验证和正常等待负责人验收均属于 `in_progress`。验证条件不可用或存在必须先由负责人解决的问题，且已无可推进动作时，转为 `blocked`。
- AI 报告完成或测试全部通过，均不替代负责人验收。负责人未回复或仅确认收到材料，不视为验收通过或取消。
- 对话轮次、会话结束、隔夜、普通休息或单个操作完成均不构成状态转换依据。“今天先停一下”保持原状态；若负责人明确要求等待新的决定才能继续，且已无可推进动作，则记录为 `blocked`。
- `review_on` 到期只要求复查，不自动解除阻塞，也不自动启动 AI。
- 归档不改变 `done` 或 `cancelled`，暂未归档也不恢复为未结束状态。

## 3. 必要内容与字段规则

每个 WI 应包含：

- 编号、标题、状态、优先级、负责人、创建日期和更新时间。
- 目标与交付物。
- 当前下一步。
- 完成标准及其对应交付物、验证方式和所需证据。
- 关联资料、启动依赖及依赖核实结果。
- 执行边界，包括允许读取和修改的范围、产物类型、允许执行的验证、不包含项和暂停条件。
- 准入审核人、日期、结论，以及明确委托后的授权记录。
- 影响后续判断的关键记录。
- 完成后的结果、验证证据和遗留问题。

字段规则：

- `status` 必填，只使用 `ready / in_progress / blocked / done / cancelled`；含义和转换条件见第 2 章。
- `owner` 必填且只有一个直接负责人，负责准入、范围调整、升级事项、验收和取消。
- `priority` 必填，只使用 `P0 / P1 / P2 / P3`，优先级由高到低排列，由负责人确认。判定参考：`P0` 为需立即处理的重大故障或紧急风险；`P1` 为当前阶段关键目标或阻碍其他已承诺工作的事项；`P2` 为正常安排的已承诺工作；`P3` 为可后置但仍已承诺的低紧迫事项。优先级不替代准入、执行委托或真实承诺日期。
- `created` 和 `updated` 必填；日期统一使用 `YYYY-MM-DD`，状态、范围、下一步、阻塞信息或关键事实变化时更新 `updated`。
- `due` 只在存在真实承诺日期时填写。
- `review_on` 用于阻塞事项的下次检查日期，状态为 `blocked` 时必填。
- `blocked_by` 记录阻塞原因或依赖事项；状态为 `blocked` 时必填，并在“当前下一步”中写明解除动作。
- 元信息中不适用的可选字段填写 `-`；正文中不适用的字段填写“不适用”，已确认不存在的资料、依赖或问题填写“无”。尚未检查的问题填写“尚未核实”，不得默认填写“无”。
- 交付物使用 `D1、D2……` 编号；完成标准使用 `AC1、AC2……` 编号，每项写明可观察的通过条件、对应交付物、验证方式和所需证据。每个交付物须有对应完成标准，执行后按 AC 编号记录验证结果及证据位置，不以“相关测试通过”等笼统表述代替具体要求。
- “准入与委托”独立记录准入审核、执行委托及 WI 维护责任和授权依据，不混入关键记录。执行委托须区分“未委托”“已委托”和“已失效”；“已委托”表示当前有效，失效时记录原因、日期和依据，重新委托时保留必要的前次委托记录；实际授权来源、日期、适用 WI 及范围须可核查。
- 启动依赖核实须记录结果及日期；无依赖时核实结果填写“不适用”。“关键记录”承载状态转换依据、范围调整批准依据、拆分关系、复查结果及误记更正等影响后续判断的事实，发生时记录日期和依据；授权事实仍以“准入与委托”为准，可相互引用。结束记录按第 5.4 节填写验收或取消决定及其依据。
- 进入 `ready` 前不得残留必填占位符；结果、验证和验收等后续才会产生的信息，分别填写“待产出”“未验证”“待验收”。未委托时明确记录“未委托”，不预填已获授权。
- `blocked` 时，“阻塞信息”须补充阻塞前是否已开始、待满足条件及解除或复查动作；原因和复查日期分别以 `blocked_by`、`review_on` 为准，解除或复查动作可引用“当前下一步”，避免重复维护。
- `ready` 和 `in_progress` 的“当前下一步”至少包含一个可在授权范围内执行、完成后可判断的动作；正常等待验收时，填写待负责人验收的交付物及证据。`blocked` 填写解除或复查动作，`done` 和 `cancelled` 可填写“无”。“当前下一步”按“动作、执行方、完成判据”填写，`done` 和 `cancelled` 填“无”时其余两项填“不适用”。`ready` 中的动作仅表示委托后的接续点，不构成启动授权。内容粒度与更新规则见第 5.3 节。

WI 不应包含：

- 从功能规格复制来的完整需求。
- 从设计文档复制来的完整方案。
- 每日流水账、大段聊天记录或发散想法。
- 可以直接从代码和 Git 获取的实现细节。

## 4. 创建与准入

### 4.1 创建粒度与拆分

调研和决策在需要跨时段跟进、独立投入和验收时应建立 WI。维护工作只有需要独立安排、委托和验收时才单独建立 WI；当前 WI 授权范围内的零星维护动作不另建任务。

一个 WI 一般应在 0.5～3 天内产生可验证结果；时间只作为异常提示，是否拆分以能否独立委托、判断和验收为准。

一个大小合适的 WI 应同时满足：

- **单一结果**：完成后的能力或结论可以用一句话说明。
- **边界有限**：负责人能够识别主要影响范围，并说明明确的不包含项。
- **决策收敛**：执行中不需要继续做尚未授权的产品、架构或风险决策。
- **证据有限**：可以通过一组聚焦的测试、演示或检查结果完成验收。
- **失败可控**：失败、阻塞或回退的影响局限在容易理解的范围内。

出现以下任一情况时应拆分 WI：

- 包含多个可以分别交付或分别验收的结果。
- 同时包含消除未知、做出方案决策和实施方案，且前一步结论会改变后一步范围。
- 不同部分可能独立完成、长期阻塞或取消。
- 包含风险等级明显不同的改动。
- 负责人无法在开始前审核边界，或无法通过有限证据判断完成。

拆分后的 WI 应保持结果依赖关系，而不是把同一个结果机械拆成无法独立验收的操作步骤。未知问题先安排范围明确的调研或决策工作；依赖其结论的实施事项暂不建立正式 WI，结论经负责人确认且实施范围通过审核后，再创建正式实施 WI。

已有 WI 拆分须由负责人确认原项与后续事项的边界：原项仍保留一个可独立交付的结果时，按第 5.2 节批准范围调整，并依据实际进展维护原状态；原项已被完全替代时，由负责人明确取消，不以“已拆分”为由标记 `done`；原项结果确已满足完成标准时，仍须按第 5.4 节验收。新 WI 分别审核准入，按所在目录确定编号。原项在“关键记录”保留拆分决定、日期、批准依据和后续事项去向，新 WI 在“关联资料”引用原项，避免重复承诺同一交付范围；未准入部分仍按候选材料管理。

### 4.2 正式建立条件

正式 WI 进入 `ready` 前，须由负责人确认：

- 目标、交付物、范围和不包含项清晰，粒度符合第 4.1 节。
- 完成标准可验证，所需验证方式和证据明确；维护 WI 须明确交付文档、工具或其他可验证结果，不能仅以“完成维护”作为完成标准。
- 负责人、优先级、当前下一步及必要关联资料已填写。
- 启动所需的资料和依赖已具备，没有阻碍当前工作开始的未决事项。
- 准入审核人、日期和结论已记录。

调研和决策 WI 的研究问题、范围和交付要求明确，即可具备启动条件，不要求提前获得结论；仍须满足上述准入条件，必须由负责人作出的选择由负责人确认。

准入不构成执行授权；执行前须取得负责人对指定 WI 和权限范围的明确委托，并记录授权依据。准入时须确认以下可委托边界：

- 可委托的产物类型、读取与修改范围及验证边界已经明确；只读任务的允许修改范围为“无”。
- 未遗留阻碍拟委托工作启动、必须先由负责人决定的问题；以支持决策为目标的 WI 应明确 AI 的交付范围、负责人决策环节及验收方式。
- 已明确超出范围、偏离已批准的行为变更或需要额外授权时的暂停条件。

## 5. 委托、执行与维护

### 5.1 责任分工与授权

负责人决定准入、范围调整、验收和取消，处理升级事项，并对 WI 状态准确性承担最终责任；AI 可以是执行者，但不替代负责人。

WI 由当前执行者维护；未委托执行或维护时由负责人维护。AI 创建或维护 WI 须有相应授权。维护授权可包含状态、更新时间、当前下一步、阻塞信息、必要执行记录和验证证据，以及依据负责人明确验收或取消结论记录终态；授权范围内无须逐次申请。

可读取不等于可修改：请求评审不授权修改文件，请求整理文档不授权实施其中的方案。文件位置、WI 正文和状态均不构成执行授权。`ready` 表示可交接；明确委托须来自当前请求或事先约定的领取范围，否则 AI 不自动领取执行。

负责人须明确委托的 WI、产物类型和权限范围，并一并明确 WI 维护责任及授权。交付物修改权限不自动包含 WI 维护权限。授权可来自本次委托或负责人已接受的长期约定，须在“准入与委托”中记录实际授权来源、日期、适用 WI 和范围；模板示例不构成授权。明确委托并记录授权后，AI 才能在相应范围内执行。

WI 维护授权不包含自行更改目标、范围、完成标准或执行权限，也不自动包含迁移、归档和配置修改。未获维护授权或本次请求明确为只读评审、检查时，AI 仅报告请求范围内的事实、建议状态和待更新内容，由负责人更新或另行委托。

### 5.2 执行审核、范围变化与暂停

开始前，负责人确认 WI 仍满足准入条件，并明确本次委托范围；完整准入清单见第 4.2 节。低风险、边界明确且容易回退的 WI，不要求单独审核执行计划；涉及跨模块架构、安全与权限、数据变更、外部副作用或难以回退操作时，AI 应先提供简短执行计划，经负责人确认后实施。

已明确授权且满足约定执行条件的动作可以继续执行，无须仅因属于以下操作类型再次申请。出现下列情况时，AI 须暂停受影响的动作并交由负责人判断：

- 扩大 WI 的功能、文件、模块或产物类型范围。
- 拟议变更超出已批准的产品行为、公开接口、数据模型、验收标准或设计范围。
- 需要尚未获相应授权的依赖新增、构建、部署或 CI/CD 配置修改、数据库迁移或数据修改。
- 需要尚未获相应授权的发布、外部系统写入、删除或其他难以回退操作，或到达约定的审批节点。
- 需要作出尚未授权且具有明显业务、架构、安全或成本差异的方案选择。
- 资料冲突超出当前调查范围、关键依赖不可用，或无法提供完成标准要求的证据。

触发暂停条件时，记录事实、影响和待决定事项；计划变化触及边界或风险时须重新确认。仍有可推进动作时可在已有授权范围内继续；只有当前授权范围内已无可推进动作时，才将整个 WI 记录为 `blocked`。

负责人批准范围调整后，由获相应授权的维护者同步更新目标、交付物、完成标准、边界和下一步，在“关键记录”保留调整前后的范围摘要、原因、批准人、日期及依据。重新核对每个交付物与 AC 的对应关系、启动依赖、执行委托和已有证据的适用性；受影响的验证结果标为待重新验证，不沿用失效证据。范围调整须重新满足第 4.2 节的准入条件，但不重置已发生的执行状态；需拆分时按第 4.1 节处理，需新授权时先补齐“准入与委托”。

### 5.3 执行记录维护

“当前下一步”是可用于恢复执行或交接的工作节点，不使用持续追加的勾选清单。AI 根据现状、工具反馈和中间结果动态决定节点内的即时步骤，字段填写要求见第 3 节。

- 状态转换依据成立后，在当前工作过程中及时更新 `status` 及依据，并同步核对当前下一步和阻塞信息，使其符合转换后的状态。状态、已确认范围、下一步、阻塞信息或关键事实变化时，同步更新对应记录和 `updated`。
- 当前节点完成、失效、推进方向改变，或进入验证、待验收、阻塞等需要改变后续动作的阶段时，更新当前下一步；等待验证或验收时写明待处理事项。
- 局部受阻但仍可推进时，在当前下一步和关键记录中说明后续动作及局部障碍。
- 进入 `blocked` 时，同步填写原因 `blocked_by`、复查日期 `review_on`、阻塞前是否已开始及待满足条件，并在当前下一步写明解除或复查动作。解除后将失效的 `blocked_by`、`review_on` 重置为 `-`，正文中失效的阻塞信息重置为“不适用”，更新当前下一步，必要经过保留在关键记录中。
- 产生影响完成标准判断或后续执行的验证结果时，及时记录对应 AC 的结果及证据位置，并更新 `updated`，不等到最终验收时集中补记。
- 同一节点内连续读取、搜索、修改、测试和修复时，不随每次操作或工具调用更新；发生上述应记录的变化时，即使节点尚未完成也须及时更新。当前下一步只保留当前接续点，必要历史进入关键记录，日常操作留在执行会话中。

`review_on` 到期时核实待满足条件并记录复查结果：仍阻塞时，更新解除或复查动作及下次复查日期；解除条件满足后，尚未开始的 WI 回到 `ready`，已开始且具有有效委托（原委托仍有效或已取得有效新委托）的 WI 回到 `in_progress`；两种情况均同步清理失效阻塞信息并更新当前下一步。已开始但尚缺有效委托时保持 `blocked`，更新待重新委托的原因、复查日期和下一步。涉及范围、权限或业务决定的解除条件须由负责人确认；解除不产生新增授权。复查后同步更新 `updated`。没有正在执行的会话、已授权并配置的自动化或其他有效执行安排时，由负责人发起复查；每周整理用于发现遗漏，不替代事件发生时的日常更新。

交接或暂停前，核对状态、当前下一步、阻塞信息和证据与实际进展一致；完整交接检查项见第 5.5 节。

### 5.4 验收、取消与归档衔接

完成后，提交实际交付结果、按 AC 编号记录的验证结果及证据位置，以及遗留问题，由负责人依据完成标准验收。完成标准未满足、必要验证未通过、缺少证据或尚未验收时，不得标记为 `done`。

验收未通过时，记录未通过项、负责人反馈及待补充证据；有可推进的修正或验证动作时保持 `in_progress`，已无可推进动作时按第 2 章转为 `blocked`。

收到负责人针对该 WI 的明确验收通过结论后，记录 `done`、验收结论、验收人、日期及依据；收到明确取消决定后，记录 `cancelled`、取消原因、决定人、日期及依据，并如实记录已交付部分、已有验证结果和遗留问题，不预填完成或验证成功。同步更新 `updated` 和当前下一步，将失效的 `blocked_by`、`review_on` 重置为 `-`，正文中失效的阻塞信息重置为“不适用”，必要历史保留在关键记录中。AI 仅在已获 WI 维护授权的范围内更新记录，不自行作出验收或取消决定。

`done` 和 `cancelled` 为终态，不直接重开；结束后新增需求、发现需处理的问题或决定恢复已取消的工作时，创建关联原项的新 WI，并重新审核准入与委托。状态或事实误记的更正不属于重开：须核实原始证据，涉及验收或取消结论时由负责人确认；获授权的维护者在“关键记录”保留更正前后内容、原因、确认人、日期和依据，同步核对下一步、阻塞信息及 `updated`，不得借更正覆盖真实历史。

先记录结束状态及依据，再按目录规范归档；归档须有相应授权。

### 5.5 交接与恢复检查

开始执行或跨会话恢复时，先读取当前 WI，核对现有状态、委托和依赖，核实可能变化的条件；不因重新打开文件而解除阻塞或重置状态。

交接或暂停前，核对状态、当前下一步、阻塞信息和证据是否与事实一致；未完成节点仍适用时可保留，并补充影响恢复执行的关键事实。交接与恢复检查如下，具体规则以对应章节为准。

| 判断事项 | 核对信息 | 对应规则 |
| --- | --- | --- |
| 要交付什么 | 单一目标、明确交付物及其位置或交付形式 | 第 1、3、4.1 节 |
| 怎样才算完成 | 可验证的完成标准、验证方式和所需证据 | 第 3、5.4 节 |
| 以什么为依据 | 实际关联资料、已确认的前置结论及启动依赖核实结果 | 第 3、4.2 节 |
| 可以读、改、执行什么 | 读取、修改及验证边界，明确产物类型和环境限制 | 第 3、5.1 节 |
| 现在是否已获委托 | 实际执行委托依据、授权范围及 WI 维护责任 | 第 5.1 节 |
| 从哪里继续 | 与实际进展一致的状态、当前下一步、影响接续的关键事实及已有验证证据 | 第 2、3、5.3 节 |
| 遇到什么需要暂停 | 暂停条件、阻塞解除条件和待负责人决定事项 | 第 2、5.2 节 |

信息不足以确定接续动作、资料不可访问、依赖失效或权限不足时，暂停受影响动作，报告缺失信息、影响和待处理事项；不得自行推定已获授权或条件已满足。已有授权范围内仍可推进的动作可以继续；已无可推进动作时记录为 `blocked`。未获 WI 维护授权时只报告事实和建议更新内容，由负责人更新或另行委托。

## 6. 工作项规范与相关资料的读取规则

本章是 WI 规则与资料的局部读取入口。[项目协作规则](../../AGENTS.md)规定何时进入本导航；进入后先仅读取本章，再按当前场景选择正文及资料，不要求预先通读全文。场景与章节的对应关系统一在本章维护。

### 6.1 场景必读内容

AI 根据本次实际需要作出的判断或动作确定场景，再读取下表所列内容及当前动作适用的其他项目规范，不因任务提及某个阶段就加载该阶段的全部规则。执行、恢复或维护已有 WI 时须读取当前 WI；只读查询、评审按判断需要读取相关内容，涉及整体一致性时再扩展。多个场景实际同时发生时，合并其读取范围；同一会话已读且未变化的内容无须重复加载。

| 场景 | 本文必读章节 | 配套资料 |
| --- | --- | --- |
| 创建或拆分 WI | 第 1～4、5.1 节及第 5.3 节的工作节点粒度要求 | [统一模板](./WI工作项文档模板.md#2-统一-wi-模板)、拟定义任务的依据；拆分时读取原 WI |
| 开始执行或跨会话恢复 | 第 1～3、5.1～5.3、5.5 节 | 当前接续动作所需资料及已有证据 |
| 日常维护 | 第 1～3、5.1、5.3 节 | 本次更新所依据的事实、决定或证据 |
| 验证、验收准备或验收检查 | 第 2、3、5.1、5.4 节 | 待验证或验收的交付物、对应完成标准及已有验证证据 |
| 结构检查、结构补齐或格式迁移 | 第 1～3、5.1 节 | 统一模板及检查或补齐所需依据 |
| 只读评审或规则解释 | 问题涉及的规则；如判断是否应为 `blocked`，读取第 2 节及相关维护规则 | 判断所需的 WI 内容、事实、决定或证据；仅摘取原文或字段不触发规范读取 |
| 维护 WI 规范或模板 | 拟修改部分及直接相关规则，按改动影响补读 | 涉及文档结构、填写提示或规范与模板对应关系时读取模板相关部分；其他资料按一致性核对需要读取 |

模板示例按填写需要读取。普通执行无需预先加载创建粒度说明、模板示例或尚未进入阶段的操作规则；出现下一节列出的触发条件时，先补读再行动。

维护规范或模板时，修改导航只需核对导航相关规则；修改状态流须进一步核对受影响的字段、执行维护、验收规则及模板对应内容。不因维护规范或模板而默认加载实际 WI 或其关联资料。

### 6.2 补读触发条件

出现下列情况时，须在采取相关动作前补读对应内容；不得先执行受其约束的动作，再补读规则。

| 触发条件 | 补读内容 |
| --- | --- |
| 新建或拆分 WI | 第 1～4、5.1 节及第 5.3 节的工作节点粒度要求；统一模板、任务依据，拆分时读取原 WI |
| 拟调整目标、范围、完成标准或粒度 | 第 4、5.1、5.2 节 |
| 发现可能超出授权、需要额外决定、依赖失效或证据无法取得等暂停情形 | 第 5.2 节；涉及状态判断时读取第 2 节 |
| 更新 WI 状态、下一步、阻塞信息、执行记录或验证证据 | 第 5.3 节 |
| 进入验证、验收准备、验收检查或处理取消决定 | 第 5.4 节及对应交付物、完成标准和证据；取消时核对实际取消依据 |
| 准备交接、暂停或恢复执行 | 第 5.5 节 |

### 6.3 上下文复用与资料展开边界

- 同一会话已读取且未变化的内容无须重复加载；场景变化时补读缺失内容，规则、WI 或相关事实变化时重读受影响部分。
- 跨会话恢复时重新读取当前 WI，读取恢复场景所需规则，核实委托、依赖及接续条件；不得仅依赖前次会话摘要。
- 关联链接作为资料入口，按当前判断或动作的需要读取，不因出现链接就递归加载全部引用。被引用且会约束当前动作的规则、前置结论和证据仍须读取，信息不足时继续补读必要部分。
- 局部读取不足以完成当前判断时，扩展至所需的最小范围；不得因局部读取遗漏适用约束，也不得因此默认展开整份文档或全部关联资料。
- 规范定义规则，模板提供文档结构和填写提示，不另行定义规则，也不能作为执行时唯一规则来源。执行约束须在规范中明确；具体任务的目标、完成标准、边界和委托依据，以已确认的当前 WI 及实际授权来源为准。
- 读取要求遵守项目访问边界，不产生额外访问、修改或执行权限；必要资料不可访问时，暂停依赖该资料的动作，报告缺失内容和影响，交由负责人处理；不得绕过访问边界。
